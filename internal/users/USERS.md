# Users

**User** - пользователь системы, аутентифицируется по email/паролю; имеет роль (```customer```/```admin```), от которой зависят права доступа в других доменах (order, payment)

## Доменная модель

Доменная модель User представляет структуру данных с набором полей:

    Id - уникальный идентификатор пользователя (генерируется в БД)
    Email - email пользователя, используется для входа
    Password - bcrypt-хэш пароля, клиенту никогда не отдаётся
    Role - роль пользователя: "customer" или "admin"
    CreatedAt - дата создания пользователя

## DTO

1. ```UserRequest``` - данные от клиента (Email, Password, Role), используется в Register и UpdateUser
2. ```UserResponse``` - ответ клиенту (Id, Email, Role, CreatedAt) - без Password
3. ```UpdateRoleRequest``` - данные от клиента (Role), используется в UpdateRole

## Ошибки домена

```InvalidPassword```, ```FailedCreatedUser```, ```FailedHashingPassword```, ```FailedToGetUser```, ```FailedToUpdateUser```, ```InvalidUserRole```

## Методы UserService

1. **Register** - хэширует пароль через bcrypt (```bcrypt.DefaultCost```), подставляет хэш вместо оригинального пароля в доменную модель, сохраняет пользователя через репозиторий
2. **Login** - получает пользователя по email, сверяет присланный пароль с хэшем (```bcrypt.CompareHashAndPassword```), при успехе собирает ```domain.Claims``` (UserId, Email, срок действия 24 часа - TODO: пробросить TTL из конфига) и подписывает JWT алгоритмом HS256 секретом из конфига
3. **GetById** - находит пользователя по идентификатору
4. **UpdateUser** - сначала проверяет, что пользователь существует (GetUserByID), затем обновляет email и пароль
5. **UpdateRole** - проверяет, что пользователь существует, что новая роль - ```"admin"``` или ```"customer"``` (иначе ```InvalidUserRole```), и обновляет роль

## Auth middleware

Проверяет заголовок ```Authorization: Bearer <token>```, парсит и валидирует JWT (HS256, секрет берётся из переменной окружения ```JWT_SECRET```), при отсутствии заголовка, неверном формате или невалидном токене - прерывает цепочку и возвращает 401. При успехе кладёт ```user_id``` в контекст запроса (```c.Set("user_id", claims.UserId)```) - именно оттуда, а не из параметров пути или заголовков, остальные домены берут идентификатор пользователя.

## ⚠️ Известный пробел: Role нет ни в JWT, ни в контексте

Сейчас ```domain.Claims``` содержит только ```UserId``` и ```Email``` - поля ```Role``` там нет вообще, и ```Login``` его в токен не кладёт. Auth middleware, соответственно, кладёт в контекст только ```user_id```, ```c.Set("role", ...)``` нигде в проекте не вызывается.

При этом order и payment домены расчитаны на то, что роль приходит из контекста (```c.GetString("role")```) для admin-проверок (```ListAllOrders```, доступ к чужому заказу/платежу и т.д.). Сейчас такая проверка всегда получит пустую строку - то есть все admin-ветки в проекте фактически недостижимы через реальный JWT-флоу.

Чтобы закрыть: добавить ```Role``` в ```domain.Claims```, прокинуть его в ```Login``` при выпуске токена, и в ```Auth``` сделать ```c.Set("role", claims.Role)```.
